# Clinic Management Prototype — Build Spec

Derived from *Clinic Management Prototype — PRD* (Nov 12, 2026). This is the first slice of the build plan (0:00–0:10): the PRD turned into something we can build from. Where this spec and the PRD disagree, the PRD wins. Points where the PRD contradicts itself are listed in [§16](#16-prd-discrepancies-resolved-here).

**Three rules apply everywhere in this spec and the code built from it:**

1. **A match is never eligibility or consent.** The matcher returns only `possible_match`, `needs_check` or `no_match`. No UI copy, code identifier, enum value, test name or seed string uses eligibility language.
2. **Consent is separate.** `reviewStatus`, `callStatus` and `consentStatus` are three independent fields. Nothing sets consent except reception recording it after the call status is `reached`. The one coupling allowed: approval sets `callStatus = needs_call`.
3. **Missing data gives `needs_check`, never `possible_match`.**

## 4. Data model

Nine clinic tables plus Better Auth's tables (`user`, `session`, `verification`, `account`). All ids are `text` primary keys (`crypto.randomUUID()`), matching Better Auth's `user.id` type. Every "who" field references `user.id`. No table has a delete path in the app.

- *Unreviewed result* = `reviewedAt IS NULL`.

- Better Auth's `admin` plugin adds `role`, `banned`, `banReason`, `banExpires` to `user` and `impersonatedBy` to `session`; these come from `auth:generate`.

## 5. Authentication

### 5.1 Server config (`src/lib/auth.ts`)

```ts
export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: "pg", schema }),
  plugins: [
    magicLink({
      disableSignUp: true,
      sendMagicLink: async ({ email, url }) => {
        await mailer.sendMail({ to: email, from: MAIL_FROM, subject: "Sign in to the clinic", text: url, html: `<a href="${url}">Sign in</a>` });
      },
    }),
    admin({ adminRoles: ["admin"] }),
    nextCookies(), // must be last
  ],
});
```

- No email/password, no social providers, no cookie cache (so a ban takes effect on the next request).
- A `hooks.before` on `/magic-link/verify` looks up whose link it is and redirects a deactivated user to `/sign-in?error=deactivated`. Without it, the admin plugin's `BANNED_USER` error reaches the browser as raw JSON (HTTP 403). The user never gets a session either way.
- `src/proxy.ts` (Next 16's name for middleware) sends any request without a session cookie a real HTTP 307 to `/sign-in`. It's an optimistic check only: `requireUser` remains the guard for session, role and deactivation. It's needed because `cacheComponents` partially prerenders pages, so a signed-out visitor would otherwise get a 200 with the redirect streamed inside it.
- `src/app/api/auth/[...all]/route.ts`: `export const { GET, POST } = toNextJsHandler(auth);`
- Client (`auth-client.ts`): `createAuthClient({ plugins: [magicLinkClient(), adminClient()] })`.

### 5.2 Sign-in flow

1. `/sign-in`: one email field. Submit calls `authClient.signIn.magicLink({ email, callbackURL: "/", errorCallbackURL: "/sign-in?error=1" })`.
2. The page always shows the same message ("If this email belongs to clinic staff, a sign-in link has been sent. Check Mailpit at localhost:8025.") so it doesn't reveal who is on staff.
3. Clicking the link in Mailpit verifies the token. With `disableSignUp: true`, an email that isn't a staff account ends at `/sign-in?error=…` with "This email isn't registered. Ask the clinic admin to add you." A banned user can't get a session (the admin plugin blocks it) and also ends on the error page.
4. `/` calls `requireUser()` and redirects to the role's default view.

### 5.3 Roles and default views (`src/lib/roles.ts`)

```ts
export type Role = "admin" | "receptionist" | "nurse" | "doctor";
```

| Role | Default view after sign-in |
| --- | --- |
| admin | `/admin` |
| receptionist | `/board?view=reception` |
| nurse | `/board?view=nurse` |
| doctor | `/board?view=doctor` |

### 5.4 `requireUser(roles?)` (`src/lib/require-user.ts`)

```ts
export async function requireUser(roles?: Role[]) {
  const session = await auth.api.getSession({ headers: await headers() });
  if (!session) redirect("/sign-in");
  if (session.user.banned) redirect("/sign-in?error=deactivated");
  if (roles && !roles.includes(session.user.role as Role)) redirect("/forbidden");
  return session.user; // { id, name, email, role }
}
```

- Called at the top of **every** page and **every** server action, with the roles from §6.
- `getCurrentUser()` calls `await connection()` before reading the session, so the session's expiry check always runs at request time, never in a prerender or prefetch (`cacheComponents` is on). Session-gated pages set `export const instant = false`.
- `/forbidden` is a static page: "You don't have access to this page." plus a link to your default view.
- A user whose `role` is missing or not one of the four is treated as not allowed anywhere except `/forbidden`.

### 5.5 Admin page (`/admin`, admin only)

**Table:** name, email, role, active (Active / Deactivated badge), actions.

| Action | Implementation | Rules |
| --- | --- | --- |
| Add staff (Dialog: name, email, role Select) | `auth.api.createUser({ body: { name, email, role }, headers })`. No password is passed (the installed version allows magic-link-only users). If the installed version rejects that, pass `password: crypto.randomUUID()` and never use it | zod: email format, role ∈ {receptionist, nurse, doctor, admin}. Duplicate email shows "Already a staff member". **Invite:** after creating the user, the action calls `auth.api.signInMagicLink({ body: { email, callbackURL: "/" }, headers })`, which emails the new staff member a sign-in link (to Mailpit). The admin's own session is unaffected. The link expires per Better Auth's default; after that, the person requests a new one on `/sign-in` |
| Change role (Select) | `auth.api.setRole({ body: { userId, role }, headers })` | An admin can't change their own role (keeps at least one admin) |
| Deactivate | `auth.api.banUser({ body: { userId }, headers })`, which revokes their sessions | An admin can't deactivate themselves (checked in the action and in the UI; the plugin also refuses) |
| Reactivate | `auth.api.unbanUser({ body: { userId }, headers })` | — |

`headers` = `await headers()` from `next/headers`. Admin can also open `/board` (read-only).

## 6. Access rules

## 7. Visit stages

```
scheduled ──check in──▶ checked_in ──nurse takes──▶ with_nurse ──send to doctor──▶ ready_for_doctor
   ──doctor takes──▶ with_doctor ──send to checkout──▶ ready_for_checkout ──complete visit──▶ done
```

Every transition is a single conditional update, `UPDATE visits SET … WHERE id = $1 AND stage = $expected`. If zero rows change, the action returns "This patient has already moved on" and the page refreshes. That makes double clicks and two staff taking the same patient safe. No transition skips a stage or goes backwards.

Implemented as `src/lib/visit-stages.ts` (pure: stage order, labels, `isAllowedTransition`) and `transitionVisit()` in `src/lib/transition-visit.ts`, which every §8 stage-changing action uses. It takes optional extra fields to write in the same statement (e.g. `nurseId`, `arrivedAt`) and extra conditions (e.g. `nurseId = me`). A non-forward `from → to` throws. Covered by `tests/visit-stages.test.ts` and `tests-db/transition-visit.test.ts` (`bun run test:db`), including 10 rounds of 5 concurrent attempts where exactly one must win.

## 8. Server actions

Every action: (1) `requireUser(roles)`, (2) zod-parse input, (3) check preconditions, (4) write, (5) `revalidatePath` for the affected pages. Errors come back as `{ error: string }` and appear in the form; they never throw raw database errors to the UI.

### 8.1 Visits (`actions/visits.ts`)

| Action | Roles | Precondition | Effect |
| --- | --- | --- | --- |
| `checkIn(visitId)` | receptionist | stage = `scheduled` | stage → `checked_in`, `arrivedAt = now()` |
| `setUrgent(visitId, urgent)` | receptionist | stage ≠ `done` | `urgent = urgent` |
| `updateContact(patientId, phone, email)` | receptionist | — | patient phone/email updated |
| `nurseTake(visitId)` | nurse | stage = `checked_in` | stage → `with_nurse`, `nurseId = me` → open nurse page |
| `saveVitals(visitId, { bpSys, bpDia, weightKg, tempC, nurseNote })` | nurse | stage = `with_nurse` AND `nurseId = me` | fields saved |
| `sendToDoctor(visitId)` | nurse | stage = `with_nurse` AND `nurseId = me` | saves the form, then stage → `ready_for_doctor` |
| `doctorTake(visitId)` | doctor | stage = `ready_for_doctor` | stage → `with_doctor`, `doctorId = me` → open doctor page |
| `saveDoctorNote(visitId, doctorNote)` | doctor | stage = `with_doctor` AND `doctorId = me` | saved |
| `addCheckoutTask(visitId, label)` | doctor | stage = `with_doctor` AND `doctorId = me` | insert task (`done = false`) |
| `sendToCheckout(visitId)` | doctor | stage = `with_doctor` AND `doctorId = me` | saves note, stage → `ready_for_checkout` |

Vitals input checks (catch typing errors only, not clinical judgments): integers for BP, `bpSys` 50–260, `bpDia` 30–160, `weightKg` 0.5–400, `tempC` 30–45, all optional; note ≤ 2000 chars.

Any doctor can take any ready-for-doctor patient. The preferred doctor is shown, not enforced.

| Action | Roles | Precondition | Effect |
| --- | --- | --- | --- |
| `markReviewed(resultId)` | doctor | `reviewedAt IS NULL` | `reviewedAt = now()`, `reviewedBy = me` |

### 8.3 Checkout (`actions/checkout.ts`)

| Action | Roles | Precondition | Effect |
| --- | --- | --- | --- |
| `toggleTask(taskId, done)` | receptionist, doctor | visit stage ∈ {`with_doctor`, `ready_for_checkout`} | `done = done` |
| `completeVisit(visitId)` | receptionist | stage = `ready_for_checkout` AND **zero** tasks with `done = false` (checked in the same transaction as the update) | stage → `done` |

### 8.4 Studies (`actions/studies.ts`)

| Action | Roles | Precondition | Effect (only these fields change) |
| --- | --- | --- | --- |
| `rerunMatching()` | doctor | — | per patient: upsert `matchStatus`, `evidenceJson`, `missingJson`, `updatedAt`. **Never** touches `reviewStatus`, `reviewedBy`, `callStatus`, `consentStatus`, `consentBy`, `notes` |
| `approveCandidate(id, note?)` | doctor | `reviewStatus = pending` | `reviewStatus = approved`, `reviewedBy = me`, `notes = note`, `callStatus = needs_call` **only if** it was `not_started` |
| `dismissCandidate(id, note?)` | doctor | `reviewStatus = pending` | `reviewStatus = dismissed`, `reviewedBy = me`, `notes = note` |

`addStaff`, `changeRole`, `deactivateStaff`, `reactivateStaff`: admin only, as specified in §5.5.

## 9. Study matcher (`src/lib/matcher.ts`)

Pure function: no database, network or clock access. `today` is passed in.

```ts
export type MatchStatus = "possible_match" | "needs_check" | "no_match";

export interface MatcherPatient {
  dob: string | null;                                   // "YYYY-MM-DD"
  conditions: { name: string; code: string | null; recordedAt: string }[];
  medications: { name: string; active: boolean }[];
  results: { test: string; value: string; unit: string | null; resultedAt: string }[];
}

export interface MatchResult { status: MatchStatus; evidence: string[]; missing: string[]; }

export function matchPatient(patient: MatcherPatient, today: string /* "YYYY-MM-DD" */): MatchResult;
```

**Criteria (clinic owner):** adult AND a documented diagnosis of diabetes.

**Definitions**

- **Documented diagnosis:** a condition where `name` contains "diabetes" (case-insensitive) OR `code`, upper-cased, starts with `E10`, `E11`, `E12`, `E13` or `E14`.
- **Diabetes signs:** a medication whose name contains "metformin" or "insulin" (case-insensitive; active or not, shown in evidence), OR a result whose test matches `/hba1c|a1c/i`.
- **Age:** whole years from `dob` to `today` on calendar dates (year difference, minus 1 if today's month/day is before the birthday's month/day). Someone turning 18 today is 18. **Adult** = age ≥ 18.
- No lab thresholds, recency rules or medication exclusions. Lab values appear as context only.

**Decision order**

| # | Condition | Status | evidence | missing |
| --- | --- | --- | --- | --- |
| 1 | dob present AND age < 18 | `no_match` | `["Age 17"]` | `[]` |
| 2 | diagnosis AND dob present (so age ≥ 18) | `possible_match` | each diagnosis + `"Age N"` + any signs | `[]` |
| 3 | diagnosis AND dob missing | `needs_check` | each diagnosis + any signs | `["Date of birth"]` |
| 4 | no diagnosis AND signs present | `needs_check` | each sign (+ `"Age N"` if dob present) | `["No documented diagnosis"]`, plus `"Date of birth"` if dob missing |
| 5 | otherwise | `no_match` | `[]` | `[]` |

**Evidence string formats**

- `Diagnosis: Type 2 diabetes (E11.9), recorded 2023-04-02` (code in brackets only when present)
- `Age 54`
- `Medication: Metformin 500 mg (active)` / `(inactive)`
- `Result: HbA1c 7.8 % on 2026-10-01 (context only, no threshold applied)`

**Writing to the database (`run-matching.ts`)**: for the single seeded study, load every patient with conditions, medications and results, call `matchPatient(p, todayLocalISO)`, and upsert on (`studyId`, `patientId`) as described under `rerunMatching` in §8.4. Rows for `no_match` patients are kept (so an earlier review isn't lost if a record changes) but are never listed.

## 10. Screens

Uses shadcn components throughout. Times are shown in local time, `HH:mm`.

### 10.1 Visit board — `/board` (FR1)

- **Scope:** visits whose `appointmentAt` falls on today (local date).
- **Columns:** patient name, reason, preferred doctor, appointment time, arrival time, minutes waiting, stage Badge, handled by, urgent Badge.
  - *Minutes waiting* = `now − arrivedAt` in whole minutes, for stages `checked_in` through `ready_for_checkout`; blank for `scheduled` and `done`. Rendered on the server with a "Refresh" button. Live updating is out of scope.
  - *Handled by:* "With nurse · Priya" (nurse's name while `with_nurse`), "With doctor · Dr Khan" (while `with_doctor`). In later stages it shows who last handled the patient (e.g. "Seen by Dr Khan").
- **Sort:** `urgent DESC, arrivedAt ASC NULLS LAST, appointmentAt ASC`. Appointment time is a tiebreak for not-yet-arrived rows and is shown for reference; it never moves an arrived patient.
- **Filter:** Tabs `All · Scheduled · Checked in · With nurse · Ready for doctor · With doctor · Ready for checkout · Done`. Default tab by `view`:
  - `reception` → shows `scheduled`, `checked_in` and `ready_for_checkout` together ("My queue")
  - `nurse` → `checked_in`
  - `doctor` → `ready_for_doctor`
  - admin / none → All
- **Row actions by role:**
  - receptionist: "Check in" (scheduled), "Mark urgent" / "Unmark urgent", "Checkout" link (ready_for_checkout)
  - nurse: "Take patient" (checked_in), "Continue" for own `with_nurse` rows
  - doctor: "Take patient" (ready_for_doctor), "Continue" for own `with_doctor` rows
  - admin: none (read-only)

### 10.2 Nurse step — `/visits/[id]/nurse` (FR2)

- Header Card: patient name, age, **reason for visit**, urgent Badge.
- Form: systolic, diastolic, weight (kg), temperature (°C), note (Textarea). Buttons: "Save", "Send to doctor".
- When the visit isn't `with_nurse` for this nurse, the page shows it read-only with a link back to the board.

### 10.3 Doctor step — `/visits/[id]/doctor` (FR3)

Order on the page is fixed. **The first thing on the page** is a Card with:

1. Reason for visit
2. Nurse vitals: BP `sys/dia`, weight, temperature, plus the nurse's name
3. Nurse note

Below it, as context:

4. Diagnoses (name, code, recorded date)
5. Active medications
6. Allergies (or "No known allergies recorded")
7. Recent results, newest first. Unreviewed ones get a highlighted row and an "Unreviewed" Badge, with an inline "Mark reviewed" button

Then the doctor's work:

8. Visit note (Textarea, "Save")
9. Checkout tasks: list + "Add task" input (placeholder "e.g. Book follow-up in 3 months"); tasks can be ticked here too
10. "Send to checkout"

### 10.4 Results to review — `/results` (FR4)

- All results with `reviewedAt IS NULL`, ordered by `resultedAt ASC` (oldest first).
- Columns: patient (link to the doctor page of the patient's visit today if one exists, otherwise plain text), test, value + unit, resulted date, "Mark reviewed" (doctor only).
- After marking, the row disappears (revalidate). Count shown in the nav: "Results (8)".

### 10.5 Checkout — `/visits/[id]/checkout` (FR5)

- Patient name, **phone, email**. Reception can edit phone/email inline (`updateContact`).
- Checkout tasks with Checkboxes; open tasks listed first.
- "Complete visit" disabled while any task is open, with the hint "2 tasks still open". Enabled when none are open (including when the doctor added none).
- No diagnoses, medications, allergies, results or nurse/doctor notes on this page.

### 10.6 Study candidates — `/studies` (FR6, "Diabetes study")

Tabs depend on role.

**Doctor: "Review" tab**

- "Re-run matching" button (shows "Matched N patients" afterwards).
- Rows: every candidate with `matchStatus ∈ {possible_match, needs_check}`. Columns: patient, match status Badge ("Possible match" / "Needs check"), evidence (list), missing (list, shown in an amber colour), review status, call status, consent status, note.
- For `pending` rows: "Approve for contact" and "Dismiss" open a Dialog with an optional note.
- Page footer text: "A possible match only means the record suggests this patient may suit the study. It is not a decision and not consent."

**Reception: "Call list" tab**

- Rows: `reviewStatus = approved` AND `callStatus ∈ {needs_call, no_answer}`. Columns: patient, phone, call status, last updated. Buttons: "Reached", "No answer".

**Reception: "Consent" tab**

- Rows: `callStatus = reached`. Shows consent status. Buttons "Consented" / "Declined" appear only while consent is `unknown`; afterwards the row shows the value and who recorded it.

Reception does not see evidence or missing lists (they contain diagnoses; see §16).

Display labels: `needs_call` → "Needs call", `no_answer` → "No answer", `unknown` → "Unknown", and so on. There is no label anywhere that implies the patient qualifies for the study.
